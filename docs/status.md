# 证据与限制

本仓库的设计处于验证中的状态。这一页记录"现在能说多少"，属于维护者资料，不进入理论正文——理论只写规则，状态与证据留在 `docs/`。

## 目前的证据

两类：

1. 对 23 份真实 skill 的归位审计（见 [placement-audit.md](placement-audit.md)）；
2. 若干次"按活动分会撞车、按提问分能切开"的实例，以及本轮写作中反复出现的跨面句子（肥规则）。

它尚未在大规模写作中被验证。

## 可被推翻的预测

如果这套坐标成立，应当能观察到：

- 同一格的 skill 可以互换，而不需要改动其他格；
- 跨格复制最终都会漂移；
- 某个项目长期缺某一格，那一格对应的事故会反复出现。

三条都可以被现实推翻，且不需要写程序去验证。

## 已知的边界

- 判据与风格的边界、对象知识归哪个面，都依赖判断，不产生唯一答案。
- 分类有争议时不代表理论错，通常代表那条规则写得肥。

## 术语 `loadout` 的审计

**定义**：一个任务实际加载的那几份 skill 的集合；运行时形成，不落盘，用完即散。

**为什么用这个词**

- `set` / `collection` 太泛，指不出"为这次任务选的"；
- `kit` 暗示一个可交付物或安装包，与"不落盘"冲突；
- `loadout` 在游戏语境里就是"这次任务带哪几样、可换"，语义正好，且不绑定任何作品。

**易混，需要限定**

- 游戏里的 loadout 常指装备与武器；本文只指 skill。
- 它不包含安装位置与可见性——那是 Skill 规范与宿主的范围。

**使用判据**：只有指"某个任务的一组 skill"时才用这个词。指单个 skill、指仓库、指一个目录，都不用。

**出现位置**：`THEORY.md`（定义）、`README.md`、`skills/skill-atlas/SKILL.md`（配一组）。

**待验证**：在没有任何解释的情况下，读者是否会把 loadout 理解成"一次任务的技能组合"，而不是"装备配置"或"一份清单文件"。
