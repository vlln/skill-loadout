# 证据与限制

这一页记录"现在能说多少"，属于维护者资料，不进入理论正文——理论只写规则，状态与证据留在 `docs/`。

核对 2026-11-01。

## 坐标本身的证据

- **归位审计**（2026-10，已归档于 [archive/placement-audit-2026-10.md](archive/placement-audit-2026-10.md)）：23 份真实 skill 逐份归位，结论是没有一条规范规则放不进三个面，但跨面的"肥句"至少五处。它直接改写了两条理论：事实与规范分开处理，肥句是常态而非反例。
- **一次真实的分组**（2026-10-31）：把三批共 23 份材料重新切成 7 份，见 `sw-dev-loadout` 仓库的 `docs/plan.md`。切分按"它主要回答哪个问题"做，四处合并、一处拆开，没有出现放不下的规则。
- **一次权威冲突被这套坐标抓出来**（2026-11-01）：该组里 `change-evidence` 与 `engineering-standards` 都声称拥有"新增一个门禁"的触发和"门禁要自证"的定义，而且前者标了 `execution`，判定句却几乎都在回答"凭什么算合格"。这是"不要让两份 skill 对同一段指令都声称权威"这条底线第一次在自己的产出上生效。
- **两组 loadout 的组内检查**（2026-11-01）：按"比描述、比判定句、按任务归还"三步各查一遍。
  - `sw-dev-loadout`（7 份）：触发短语无逐字重复；话题层面四处共享（PR、失败、文档、范围）经查都是一方给定义、另一方给一句应用。只有门禁那一处是真冲突，已修。
  - 本仓库（5 份）：九个话题跨份出现，逐条核对后都是"定义在一份、应用在另一份"的形态——面的定义在 `skill-atlas`，`skill-making` 只在定坐标那一步用一句；改进回路的定义在 `improvement-loop`，`skill-making` 的验收阶段只写它需要的最小版。没有需要改的。
  - 这说明"共享内容各自写最小充分版"在实践中成立，但判断共享是定义还是应用必须逐句读——机械计数只能给出候选，给不出结论。

## 方法的证据

两个真实产品，三轮同题对照，记录在各自仓库：

- `readme-skill/docs/experiment.md`：同一个仓库、同一句任务，四个版本 354 → 372 → 148 → 140 行。结论是"能执行的判据都生效了，没写下的判据完全没生效"——体量判据写成数字之后，行数才掉下来。
- `sw-dev-loadout/docs/experiment.md`：四轮。审 diff 打平（6/6），写计划更完整但篇幅翻倍，执行计划时暴露 16 处问题含 4 处自相矛盾，换夹具后抓到基线的两条新用例在旧版本上就通过。各轮都逼出一条规则。

## 这些证据有多硬

- 每一轮都只跑了一次，没有测同一夹具重跑的波动。所以数字只能说明方向，不是效应量。
- 写 skill、造夹具、跑对照用的是同一个模型，对照的盲点与 skill 的盲点重合。
- 四条补进去的规则里，只有「新证据必须在改动前的版本上真跑一遍」在两个夹具上都出现过，算确认；其余三条仍是单夹具候选。
- 第四轮为验「按规模裁剪」刻意选了小任务，结果两组都克制、测不出差别。**夹具要能让被验的规则有机会失效**，否则跑了也是白跑——这是这一轮最实际的教训。
- 触发没有实测命中率，也没做新会话冒烟；描述是人工按真实请求判的。
- 坐标部分的证据全部来自归位与切分，**没有一次是"换掉同一格的一份、其余不动"的真实替换**——下面第一条预测因此仍然未测。

## 可被推翻的预测

- 同一格的 skill 可以互换，而不需要改动其他格；
- 跨格复制最终都会漂移；
- 某个项目长期缺某一格，那一格对应的事故会反复出现。

三条都可以被现实推翻，且不需要写程序去验证。第二条在 `sw-dev-loadout` 里有一个可观察的样本：七份里共用的规则各写了最小充分版，下一次改动时看它们是否开始各说各话。

## 已知的边界

- 合格线与写法的边界、对象知识归哪个面，都依赖判断，不产生唯一答案。
- 分类有争议时不代表理论错，通常代表那条规则写得肥。
- 坐标不管好坏：一份站位清楚的 skill 可以内容很差。效果要靠对照实验，不靠归位。

## 术语 `loadout` 的审计

**定义**：一个任务实际加载的那几份 skill 的集合；运行时形成，不落盘，用完即散。

**为什么用这个词**

- `set` / `collection` 太泛，指不出"为这次任务选的"；
- `kit` 暗示一个可交付物或安装包，与"不落盘"冲突；
- `loadout` 在游戏语境里就是"这次任务带哪几样、可换"，语义正好，且不绑定任何作品。

**易混，需要限定**

- 游戏里的 loadout 常指装备与武器；本文只指 skill。
- 它不包含安装位置与可见性——那是 Skill 规范与宿主的范围。

**使用判据**：只有指"某个任务的一组 skill"时才用这个词。指单个 skill、指仓库、指一个目录，都不用。

**出现位置**：`THEORY.md`（定义）、`README.md`、`skills/skill-atlas/SKILL.md`（配一组）。

**待验证**：在没有任何解释的情况下，读者是否会把 loadout 理解成"一次任务的技能组合"，而不是"装备配置"或"一份清单文件"。
