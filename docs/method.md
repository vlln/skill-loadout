# 从选题到 loadout：一条可重复的制作方法

这份文档记录一次真实制作（`readme-writing`）里有效、可复用的步骤。它不是理论，是操作记录；等它在第二个、第三个选题上复现，再考虑升级成 skill。

## 0. 什么选题值得做

三个条件同时成立才做：

- **反复出现**：同一类任务会被反复要求，不是一次性；
- **有真实材料**：能拿到真实产出、真实代码、真实用户抱怨；
- **效果可观察**：做得好不好，能在一份具体产出上指出来。

反例：主题太宽（"写文档"）、效果无法观察（"品味"）、没有对照物（"更专业"）。

## 1. 选题：把任务写成"可判的失败"

不要写"做一个 X skill"，写"agent 在没有约束时会犯哪几类错"。

`readme-writing` 的选题是三条失败：**丑**、**信息层级错**（把工程内容混进 README）、**对读者不友好**。三条都能在后来的产出里被指认，所以它们后来直接变成了判据。

选题阶段产出一句话：

> 这个 skill 要阻止的三类具体失败是什么？

写不出三类，说明选题还没成形。

## 2. 定坐标：先定面，再定用途

- 它主要回答哪个问题（流程 / 质量 / 执行）？
- 它替谁、在什么任务里用？这句话要能直接写进 `description`。
- 它需要自己保存事实、自己取得许可吗？

只标一个面；用途写进描述的前 500 字符。

## 3. 收集信息：三种材料，缺一不可

| 材料 | 它给什么 | 缺了会怎样 |
|---|---|---|
| **规范/标准** | 事实与硬约束（字段、上限、宿主行为） | 判据没有根据，写出来是个人口味 |
| **同类实现** | 形态、结构、反例（流行 skill、高星项目） | 写出来干巴巴，不知道别人怎么做 |
| **真实运行** | 可复制性与真相（真装、真跑、真输出） | 命令照抄必失败，断言来自想象 |

规则：

- **事实带来源与日期**；打不开的来源单列一节记"未使用"，不要删掉痕迹。
- 三条材料都读过再动笔。只做"同类实现"最容易——也最容易抄错。

## 4. 写第一版：规则来自材料，不来自模型

- 每条判据都要能回答"违反了会怎样"。
- 一条规则只回答一个问题；肥句先拆成两条。
- 结构：事实 / 判据 / 反例 / 自检。
- **第一版一定会漏。** 漏不是问题；没有实验才是。

## 5. 实验：同题重复，只改一个变量

这是整套方法里最有效的技巧。

- 同一个真实仓库、同一句任务、同一条禁令（不许看现有产出），产出到**不同文件**。
- 至少两组：**基线**（不给 skill）与**处理组**（给 skill）。
- 基线也要认真做，否则对照失效；处理组**不知道基线存在**，否则会锚定。
- 度量要可数：行数、章节数、代码块、图片、徽章、源码引用、某类段落的有无。

实际跑出的曲线：

| 版本 | 方法 | 行数 | 节数 |
|---|---|---|---|
| A | 无 skill | 354 | 15 |
| B | skill v0.1 | 372 | 10 |
| C | skill v0.2（加体量判据） | 148 | 7 |
| D | skill v0.2 + 模仿高星项目 | 140 | 7 |

**只看 B 会误判**：B 有了徽章、可复制安装块、首屏纪律，看起来已经成功；只有和 A 比、再看 C，才知道它没解决体量。

## 6. 迭代：只改"没发生"的判据

B → C 的教训，一句话：

> **能执行的判据都生效了；没写下的判据（体量）完全没生效。**

所以迭代不是"把 skill 写得更好"，而是：

1. 找出一个**本该生效却没写**的判据；
2. 把它写成可判的（数字、有无、能否原样执行）；
3. 重跑同题实验，看度量是否移动。

加判据的顺序：**可数**（行数、节数、张数）→ **可指**（有没有某类段落）→ **可跑**（命令能否逐字执行）。一次只加一条，才能归因。

## 7. 收敛：什么时候停

- 连续两轮，处理组在度量上不再变化；
- 新判据不再产生新行为；
- 剩下的问题属于**判断**而不是规则（品味、取舍）——把这些写进说明，不要硬写成判据。

## 8. 自动化的形状

把上面八步写成 agent 可执行的循环：

```
选题（三类失败）
  → 材料（规范 / 同类 / 真跑）
  → v1
  → 实验（1 基线 + 1 处理，同题同禁令）
  → 差异归因（哪条判据改了哪句）
  → 加一条判据
  → 重跑
  → 收敛 → 交付 + 证据
```

需要三样基础设施：**可重复的任务夹具**（同仓库、同禁令、不同输出）、**度量脚本**、**判据到可观察差异的映射**。

最大的风险是 Goodhart：agent 会优化度量而不是质量。对策是让度量只负责"发现缺口"，最终判断仍由人看一份真实产出。

## 9. 这一轮踩到的坑

- 让子代理"用 loadout"，它可能只读不用 → 要求它报告**哪条判据改了哪一句**。
- 两次产出写同一个文件会互相覆盖 → 每次独立文件。
- 基线偷懒 → 对照失效；给基线同样的详尽要求。
- 只测"制作"不测"效果" → 第一轮实验就这样，直到同题 A/B 才见真章。
- 校验器只看 exit 0 → 必须做负控（删字段、改目录名、加自造字段）。
- 体量判据写"别太长"没用，要写数字（≤150 行、`##` ≤8）。

## 10. 可复用的实验模板

**基线**

> 你的任务：为 `<仓库>` 写一份 README。不要读现有 README。只写你核实过的内容，没有的素材不要编造。产出到 `<文件 A>`。

**处理组**

> 同上，但先完整读 `<skill 路径>` 并照它做；交付前逐条过它的自检。产出到 `<文件 B>`。

**判定**：先看度量差（行数、节数、装饰、工程段落），再读首屏与章节顺序，最后看处理组能不能说出"哪条判据改了哪一句"。说不出来，说明它没用 skill，只是碰巧写得好。
