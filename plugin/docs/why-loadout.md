# 为什么是编组：两个结构性的好处

这不是功能清单，是两条结构变化。理解它们之后，插件里每个设计取舍都能对上。

## 一、管理复杂度：从 O(技能数) 到 O(任务类型数)

技能一多，旧模型的所有管理办法都在**优化检索**：目录、标签、注册表、评分。它们默认你最终仍要面对这个列表。

编组换了个前提：日常你不需要面对列表。装一百个技能，日常面对的是"论文阅读""写插件""发版"这几个编组。列表和搜索仍然存在——但只在**整理库存**时用，不在每次任务里用。

管理复杂度因此不再随技能数线性增长，而是随**任务类型数**增长。两者不是一个量级。

## 二、成本结构：把"装"和"用"拆开

旧模型里两者绑死：装进发现根 = 每个会话都加载。于是多装有真实代价——每张卡占上下文、可能误触发。理性做法是克制安装。

会话按编组选择把两者拆开之后：

- **装 = 入库**。多装的代价接近零：不加载就不占上下文、不会误触发。
- **用 = 装配**。只有当前会话所选编组的成员才通过本插件生效，多组共享成员去重。

直接后果：囤积变得无害，"先收着以后可能有用"从负债变成资产。间接后果：技能生态的激励从"克制收集"变成"鼓励收集"，于是编组的组织质量变成真正的门槛——库房越大，装配越重要。

## 这两条之后的取舍（插件里已经这样做了）

- 插件页仍保留完整的库存管理（发现、安装、分类、搜索、清理）——它是**库房**，不是日常入口。
- 日常入口是编组：一个会话可选多个组，按并集提供技能；取消某组仍保留其他组需要的成员。
- 编组对用户可见可读（成员清单、缺失标记），因为暗知识会让库房重新变成黑盒。
