# 制作一个 skill 的流程

这份 skill 管什么时候做哪一步、谁决定、交接什么。

| 阶段 | 产出 | 过关条件 | 谁决定 |
|---|---|---|---|
| 0 决定 | 一句话：反复任务 + 知识缺口 | 一段常驻规则不足以替代 | 人，或人明确委托 |
| 1 提取 | 真实步骤、纠正、输入输出、项目事实 | 有模型猜不到的、来自真实工作的材料 | agent |
| 2 拆 | 一份，或几份带边界的清单 | 每份都能一句话说清何时用 | agent |
| 3 写 | `SKILL.md` 初稿 | 字段与文字达到合格线 | agent |
| 4 验收 | 校验结果 + 查询集测试 | 负控会失败；该中中，近邻不中 | agent，异常交人 |
| 5 发布 | 可安装的源 + README | 干净环境照 README 能装成 | **人** |
| 6 维护 | 版本与复查记录 | 事实未过期，或已更新 | agent 提议，人确认发布 |

## 0 决定：要不要做

做，当至少一条成立：同一套指令反复被粘进对话；需要模型猜不到的领域或项目知识；顺序脆弱、命令精确、有校验关口；要在多个仓库或宿主间共享。

不做：一次性任务；稳定偏好（该进常驻规则）；模型已经做得很好；内容其实是某个工具的实现。

写不出一句话说明"它替谁省掉什么"，就是不该做。

## 1 提取：从真实工作里拿材料

**不要从零让模型"生成一个 skill"**——那是产出"注意边界、遵循最佳实践"这类空话的最快路径。先有一次真实使用，再提炼。

- 做完一次真实任务，记下：走通的步骤、你做的纠正、输入输出的形状、你补充的项目事实。
- 有现成材料就从材料提炼：内部文档与 runbook、API 与配置、评审意见、版本历史里的修复、真实故障与处置。
- 逐个例子问三件事：哪段会被反复重写（→ 脚本）、哪些事实模型猜不到（→ 正文或 gotchas）、哪些输入输出格式固定（→ 模板）。

## 2 拆：一份还是几份

拆的信号：两个任务永远不会同时激活；描述必须用 `and` 连接两件无关工作；维护者说不清改动该落到哪一份。

不是拆分信号的：两份 skill 抢同一个触发——那是描述问题，先改描述。

拆完每份写清"不负责什么"；共享内容各自写最小充分版，不互相引用。

## 3 写

本阶段只定两件事：它回答哪个问句（主面）、它在讲什么东西（作用域）。定不出来就先别写。

## 4 验收：让触发可测

- 机械：`skills-ref validate`、`name` 与目录一致、正文行数在限内。
- 负控：故意改坏一处，确认检查会报错。
- **查询集**：造约 20 条真实请求——8–10 条应触发，8–10 条是**近邻**不应触发（近邻比明显无关的请求更有价值）。每条跑 3 次，算命中率；应触发的高于 0.5、不应触发的低于 0.5 才算过。
- 只改训练集上失败的描述：约 60% 训练、40% 验证；约 5 轮或验证不再提升就停。
- 没有可观测的加载轨迹时退回冒烟：新会话装好，问一句应触发的，确认加载；再问一句近邻，确认没加载。

## 5 发布

- **版本**：只改措辞 → patch；新增指导或改变某类任务的做法 → minor；改契约（描述语义、输入输出、依赖、兼容性）→ major。未发布的实验不升版本。
- **卫生**：无密钥、无构建产物与缓存、仓内相对链接、清单与徽章真实（列表页真的存在并能链回）。
- **权限**：`allowed-tools` 是许可授予，不是沙箱；发布前重审，第三方来源先看再跑。
- **README 必须能让人独立装上**：真实源形式、一行一条、写清前置条件/装后行为/卸载；在干净环境照 README 走一遍。README 只写给人看的东西，不放 agent 工作流与内部设计。
- 发布、推公共仓库、加徽章、声明兼容性，需要人明确同意；之前的同意不延伸到新动作。

## 6 维护

复查触发：宿主或规范升级、引入新依赖、满复查周期（默认 60 天）、出现漏触发或误触发。

- 用真实任务再跑一遍，读执行轨迹而不只看结果——看不懂的步骤通常说明指令太含糊或没给出默认。
- 只做三件事：重核带日期的事实、看描述是否仍命中真实请求、删掉不再成立的建议。不要为了显得在维护而加内容。

## 不负责

写法与字段的合格性、定位与重叠判断、安装与清单命令，都不在本文范围内。
