# 内容定位

给 skill 定位只用两步：先问它回答哪个问题（面），再问它的内容在讲什么东西（作用域）。定位之后，重叠、拆分、配组才有依据。

这两个字段是给人做判断用的透镜，不是给程序做校验的接口。不设默认值，不要求必填，没有校验脚本。

## 面：三个问句

| 面 | 问句 | 它产出 |
|---|---|---|
| `process` | 什么时候做、由谁决定、承诺是什么、怎么交接 | 承诺、授权、关口、变更与恢复点 |
| `quality` | 凭什么算合格、怎么写画得更好 | 判据、评审结论、写作与界面判断 |
| `execution` | 用什么做、跑哪条命令、产物在哪 | 命令、工具、环境、证据 |

质量面内含两类规则：**判据**（什么算错、合格线）与**风格**（怎么写更好）。它们可以同处一份 skill，但正文要分得清——两者的替换周期不同。

流程与执行回答的是完全不同的问题，不能在同一条规则里混着写。

## 判据：一条规则只回答一个问题

**肥规则是常态。** "每个非平凡改动必须在同一个 PR 内新增一条记录"——前半句是流程（何时必须做），后半句是质量（记录长什么样）。见到这种句子，先拆句，再归属；不要因为它跨面就断定分类不够用。

## 作用域：内容所指对象的种类

| 标识 | 在讲什么 | 判据 |
|---|---|---|
| `method` | 怎么做，与具体对象无关 | 换个对象，规则仍成立 |
| `subject` | 某类对象是什么样 | 只对一类对象成立，但对其中任意个体成立 |
| `instance` | 某个具体实例的事实 | 换个实例就不成立 |

**举例不改变作用域。** 讲方法的 skill 里出现某个仓库的命令作例子，它仍是 `method`；只有"规则本身成立的范围"决定作用域。

**对象知识归哪个面**，看读者拿它做什么：拿去判断"这样算不算合格"，归质量；拿去动手"该跑什么、装在哪"，归执行。同一事实可以在两处被引用，但只能有一个家。

扩展标识必须命名一个可指认的对象（框架、平台、产品族、领域、组织、仓库），不能比 `method` 更宽，且首次出现时在 `description` 里说明它指什么。

## 标注

```yaml
face: quality        # process | quality | execution
scope: method        # method | subject | instance，或一个可指认的扩展标识
```

一份 skill 只标一个主面。标不出来，说明它想同时回答两个问题——该拆，而不是该标两个。

## 四个常用动作

**定位一份。** 读它回答的问题，给出结论：`它回答 X，作用域 Y，另外触及 Z（拆分候选）`。触及的 Z 要具体到句子，不要只写面名。

**判断重叠。** 两份 skill 命中同一个问句且服务同一作用域，就是重叠；同一条规则在两个文件里各写一遍，是复制，最终会漂移。可比性不需要看篇幅，只看问句与"不负责什么"。

**拆分。** 沿"流程 / 质量 / 执行"的缝切；质量内部的判据与风格只需在正文分区，不必拆成两份。切完检查一遍：有没有一条规则两边都放不下？有，说明缝切错了。

**配一组。** 为一类任务配齐三面，每份写清"不负责什么"；共用规则引用，不复制；最后用三句真实的请求试一遍，看会不会同时命中两份。

## 边界

- 不规定覆盖层级：装在哪、谁可见，由 Skill 规范与宿主决定。
- 不做门禁：没有程序能判断一条规则属于哪个面，判断只能由人或有判断力的 agent 做。
- 不强制组合：组合是坐标的结果，不是它的要求。
