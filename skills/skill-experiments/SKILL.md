# 用同题实验把 skill 调到有效

一份 skill 能装上、能触发，不等于它改变了产出。这份 skill 管的是**证明与迭代**：同题跑对照，找到真的生效的那条判据，把它补成规则。

## 事实：一次真实实验的四版

同一仓库、同一任务（重写 README）、同一禁令（不许看现有产出），只改 skill：

| 版本 | 方法 | 行数 | 节数 |
|---|---|---|---|
| A | 无 skill | 354 | 15 |
| B | skill 初版 | 372 | 10 |
| C | 加体量判据 | 148 | 7 |
| D | 加体量判据 + 模仿高星项目 | 140 | 7 |

两条结论（核对 2026-10-31）：

- **能执行的判据都生效了**：可复制安装、首屏纪律、不搬测试数字，在 B 就出现了。
- **没写下的判据完全没生效**：B 没有任何关于体量的规则，于是 372 行；加上"≤150 行、`##` ≤8"后，C 落到 148。

只看 B 会误判成成功。**必须有基线，也必须看第二轮。**

## 实验设计

- 同一个真实输入、同一句任务、同一条禁令；产出写到**不同文件**，否则互相覆盖。
- 至少两组：基线（不给 skill）与处理组（给 skill）。要比两个版本时，两组都给 skill，只差一条判据。
- **基线也要认真做**，否则对照失效；**处理组不要知道基线存在**，否则会锚定。
- 一次只改一条判据，否则无法归因。

## 度量

先量可数的，再读不可数的：

| 类型 | 量什么 | 用来看 |
|---|---|---|
| 可数 | 行数、章节数、代码块、图片、徽章、对源码的引用 | 结构是否真的变了 |
| 可指 | 某类段落的有无（实现细节、测试数字、流程叙述） | 该走的走了没有 |
| 可跑 | 命令能否逐字执行、输出是否是真实运行 | 是否只是看起来像 |

**归因**：实验结束后问处理组"哪条判据改了你哪一句"。答得出，说明判据在起作用；答不出，说明它只是碰巧写得好。

## 迭代

不要问"怎么把 skill 写得更好"，问：**哪条本该生效的判据没有写下来？**

1. 从对照组找差异：处理组做到了什么、基线没做到什么——那条差就是缺的判据。
2. 写成可判的形式，顺序是 **可数 → 可指 → 可跑**：先能用数字判，再能用有无判，最后才要求能原样跑。
3. 重跑同题，看度量是否朝预期移动；没动，说明判据写得太软（"别太长"没有用，"≤150 行"才有）。

## 收敛

同时满足三条就停：

- 连续两轮，处理组在度量上不再变化；
- 新加的判据不再产生新行为；
- 剩下的差异属于判断而非规则（品味、取舍、风格选择）。

第三条的东西写进 skill 的说明，不要硬写成判据——写成判据只会让下一轮无法判定通过与否。

## 陷阱

- **只测"制作"不测"效果"**：证明"用这套方法能产出一份合格 skill"很容易，证明"这份 skill 让产出变好"必须跑对照。
- **基线偷懒**：给基线同样的详尽要求和同样的读者定义，否则差异来自努力程度，不来自 skill。
- **Goodhart**：agent 会优化度量而不是质量。度量只用来发现缺口，最终判断仍要看一份真实产出。
- **把巧合当因果**：处理组变好但答不出"哪条判据改的"，按未生效处理。

## 输出

一份实验记录，四样东西：

1. 每版的产出（原文件，不删）；
2. 对照表（版本 × 度量）；
3. 每条判据的证据：它改了哪一句、哪一节、哪一版；
4. 收敛判断：哪三条满足，剩下的哪一点属于判断。

有了这四样，下一轮的改动才有依据；没有它们，迭代只是重写。
