# 制作 skill 的流程

这份 skill 管什么时候做哪一步、谁决定、交接什么。一份和一组走同一条线；做一组时多一张地图和一次组内检查。

| 阶段 | 产出 | 过关条件 | 谁决定 |
|---|---|---|---|
| 0 决定 | 一句话：反复任务 + 它要挡住的几类错 | 能列出至少三类具体失败；一段常驻规则不足以替代 | 人，或人明确委托 |
| 1 提取 | 真实步骤、纠正、输入输出、项目事实 | 规范、同类实现、真实运行三种材料都读过 | agent |
| 2 地图 | 每份一行：主面、回答的问题、触发场景、材料落点 | 每个话题只有一个主人 | agent，交人过目 |
| 3 写 | `SKILL.md` 与 references 初稿，冻结一份副本 | 字段与文字达到合格线 | agent |
| 4 验收 | 校验结果、触发测试、效果对照 | 负控会失败；对照里能指出哪条规则改了哪句 | agent，异常交人 |
| 5 发布 | 可安装的源 + README | 干净环境照 README 能装成 | **人** |
| 6 维护 | 版本与复查记录 | 事实未过期，或已更新 | agent 提议，人确认发布 |

**流程深度与规模成比例。** 一份只给自己用、只改措辞的 skill，可以跳过地图和效果对照，只做机械校验与一次冒烟；面向他人发布的一组，七个阶段都要走。裁剪时在记录里写一句跳过了什么、为什么。

## 0 决定：要不要做

做，当至少一条成立：同一套指令反复被粘进对话；需要模型猜不到的领域或项目知识；顺序脆弱、命令精确、有校验关口；要在多个仓库或宿主间共享。

不做：一次性任务；稳定偏好（该进常驻规则）；模型已经做得很好；内容其实是某个工具的实现。

把选题写成"agent 没有它时会犯的几类错"，而不是"做一个 X skill"。这几类错后面会直接变成判据和对照实验的度量。

## 1 提取：从真实工作里拿材料

**不要从零让模型"生成一个 skill"**——那是产出"注意边界、遵循最佳实践"这类空话的最快路径。先有一次真实使用，再提炼。

三种材料缺一不可：

- **规范与标准**：事实与硬约束（字段、上限、宿主行为）。缺了，判据只是个人口味。
- **同类实现**：成熟项目与流行 skill 的形态与反例。缺了，写出来不知道别人怎么做。
- **真实运行**：真装、真跑、真输出。缺了，命令照抄必失败。

逐个例子问三件事：哪段会被反复重写（→ 脚本）、哪些事实模型猜不到（→ 正文或 gotchas）、哪些输入输出格式固定（→ 模板）。事实记下来源与核对日期；打不开的来源单列，不删痕迹。

从现有材料提炼时，**逐条记下删了什么、为什么删**。提炼最常见的缺陷不是写错，而是悄悄丢掉一条适用条件（"小改动可以简化"这类），让剩下的规则在所有规模上都变成硬要求。

## 2 地图：先定谁管什么，再动笔

做一组时，先写一张表，每份一行：名字、主面、它主要回答的问题、触发场景、从哪些材料来。再按话题列一张归属表：每个话题（例如"新门禁要证明自己会拒绝"）只能有一个主人，其余份最多保留自己任务需要的一句应用。

拆的信号：两个任务永远不会同时激活；描述必须用 `and` 连接两件无关工作；维护者说不清改动该落到哪一份。

不是拆分信号的：两份 skill 抢同一个触发——那是描述问题，先改描述。

只做一份时，这一步缩成两句：它回答哪个问题（主面），它替谁在什么任务里用（写进 `description`）。

## 3 写

按地图写，每份只写自己的话题。写完**冻结一份副本**（例如 `docs/v1/`），后面每一轮改动都拿它对照；没有冻结的基线，"变好了"无从证明。

## 4 验收

三层，从便宜到贵：

**机械。** 校验器通过、`name` 与目录一致、正文行数在限内。再做负控：故意改坏一处，确认检查会报错。

**触发。** 造约 20 条真实请求——一半应触发，一半是**近邻**不应触发（近邻比明显无关的请求更有价值）。每条跑 3 次算命中率；应触发的高于 0.5、不应触发的低于 0.5 才算过。只改失败的描述，约 60% 训练、40% 验证，约 5 轮或验证不再提升就停。没有可观测的加载轨迹时退回冒烟：新会话装好，问一句应触发的，确认加载；再问一句近邻，确认没加载。做一组时，再把每份描述的触发短语并排比一遍，同一短语不应出现在两份里。

**效果。** 同一个真实任务，两组互不可见：基线不给 skill，处理组给 skill，产出到不同文件，基线同样认真做。先比可数的差异，再读产出，最后要求处理组说出"哪条规则改了哪一句"——说不出，就是碰巧写得好。

效果对照要跑到**下游**：如果 skill 的产出是计划、规范或清单，就把它交给另一个 agent 照着执行一次。纸面自洽的计划，常在执行时才暴露两条规则不能同时成立。

对照打平不是失败：它说明这份 skill 在这类任务上没有增益，该写进记录，而不是继续加规则去追。

## 5 发布

- **版本**：只改措辞 → patch；新增指导或改变某类任务的做法 → minor；改契约（描述语义、输入输出、依赖、兼容性）→ major。未发布的实验不升版本。
- **卫生**：无密钥、无构建产物与缓存、仓内相对链接、清单与徽章真实（列表页真的存在并能链回）。
- **名字**：发布前查目标宿主的已装列表，同名 skill 会按宿主的优先级互相覆盖。
- **权限**：`allowed-tools` 是许可授予，不是沙箱；发布前重审，第三方来源先看再跑。
- **README 必须能让人独立装上**：真实源形式、一行一条、写清前置条件、装后行为与卸载；在干净环境照 README 走一遍。README 只写给人看的东西，不放 agent 工作流与内部设计。
- **实验材料随仓库走**：夹具与对照记录放进仓库，别人才能复现"它有效"这句话。
- 发布、推公共仓库、加徽章、声明兼容性，需要人明确同意；之前的同意不延伸到新动作。

## 6 维护

复查触发：宿主或规范升级、引入新依赖、满复查周期（默认 60 天）、出现漏触发或误触发。

- 用真实任务再跑一遍，读执行轨迹而不只看结果——看不懂的步骤通常说明指令太含糊或没给出默认。
- 只做三件事：重核带日期的事实、看描述是否仍命中真实请求、删掉不再成立的建议。不要为了显得在维护而加内容。
- 一次真实运行逼出的新规则，先记为候选；在另一个任务上再出现一次，才算确认。只被一个夹具逼出来的规则，可能只是在拟合那个夹具。
